เราแก้ปัญหาอะไร และใครดูส่วนไหน

เมื่อโปรแกรมเรียกใช้ page ที่ยังไม่อยู่ในหน่วยความจำและ frame เต็ม ระบบต้องเลือก page เดิมออก งานนี้ทดลองว่ากฎการเลือกต่างกันทำให้สถานะ frame และจำนวน page faults ต่างกันอย่างไร และค้นหา input ที่แสดงความแตกต่างนั้นได้

เข้าใจภาพรวมทุกคน แต่ไม่ต้องจำโค้ดทุกบรรทัดเท่ากัน

ทุกคนควรคำนวณตัวอย่างด้วยมือ อธิบายสาม algorithms และสาธิตโปรแกรมได้ ส่วนที่รับผิดชอบต้องอธิบายได้ลึกถึงตัวแปร ฟังก์ชัน เหตุผลการออกแบบ และการตรวจความถูกต้อง

เส้นทางข้อมูลที่ต้องเล่าให้ได้

เลือก inputโหลดไฟล์จาก results / path หรือค้นหา reference string ใหม่
ตั้งค่าทดลองเลือกจำนวน frames และ algorithm หรือเงื่อนไขค้นหา
คำนวณด้วย enginesimulate() คืน Stats และส่ง Step ผ่าน callback เมื่อมีผู้รับ
อ่านผลและทำซ้ำดูตาราง เหตุผล จุดที่ต่างกัน แล้วบันทึก reference string

ขอบเขตของโปรแกรมปัจจุบัน

จำลอง reference string หนึ่งชุด เริ่มด้วย frame ว่างทุกครั้ง รองรับ FIFO, LRU, Optimal, 1–10 frames และไฟล์สูงสุด 1,000 references ส่วน search จำกัด 1–6 page IDs, ความยาว 1–12 และไม่เกิน 100,000 candidates ไม่มีการจำลอง address translation, TLB, dirty bit, disk timing หรือหลาย process

ฟีเจอร์ที่ทำแล้ว: โหลด/บันทึกไฟล์, browse results, จำลองทีละขั้น, สรุปผล, frame sweep, ค้นหา input และวิเคราะห์ FIFO/LRU ในแถวเดียวกัน ส่วนบันทึก metadata และ export CSV ที่เคยเสนอ ยังไม่ใช่ฟีเจอร์ของเวอร์ชันนี้

02

ความเข้าใจร่วมกันของทั้งสามคน

ศัพท์ที่ต้องพูดเป็นภาษาของตัวเอง

คำความหมายในงานนี้ตัวอย่าง
Page / FramePage คือหน่วยข้อมูลที่ร้องขอ ส่วน frame คือช่องในหน่วยความจำที่เก็บหนึ่ง pagePage 7 อยู่ใน frame 2 ได้ หมายเลข page ไม่ได้กำหนดตำแหน่ง frame
Reference stringลำดับหมายเลข page ที่เรียกใช้จากซ้ายไปขวา1 2 1 3 1
HitPage ที่ร้องขออยู่ใน frame แล้ว[1, 2] เรียก 1 → Hit
FaultPage ที่ร้องขอยังไม่อยู่ใน frame[-, -] เรียก 1 → Fault แม้ยังว่าง
Replacement / Victimเมื่อเต็มต้องเลือก page เดิมออก; victim คือ page ที่ถูกเลือก[1, 2] เรียก 3 → อาจเอา 1 ออก
Localityการกลับมาใช้ข้อมูลเดิมหรือข้อมูลใกล้กันเป็นพฤติกรรมที่มีผลต่อนโยบาย memoryInput แบบใช้กลุ่มเล็กซ้ำ ต่างจาก input ที่ไล่ page ใหม่ทั้งหมด งานนี้ใช้ page IDs จึงไม่ได้จำลองระยะห่าง address โดยตรง

FIFO

เอา page ที่เข้ามาก่อนสุดออก

Hit ไม่เลื่อนคิว เพราะเวลาที่เข้าไม่เปลี่ยน

LRU

เอา page ที่ไม่ได้ใช้งานมานานที่สุดออก

Hit ต้องอัปเดต เพราะเป็นการใช้งานล่าสุดใหม่

Optimal

เอา page ที่จะใช้อีกไกลที่สุดในอนาคตออก

ต้องรู้อนาคต ใช้เป็น benchmark จำนวน faults

ตัวอย่างที่ทุกคนต้องคำนวณได้: 2 frames

ใช้ 1 2 1 3 1 แล้วตอบก่อนเปิดโปรแกรมว่าแต่ละขั้นเป็น Hit/Fault และ page ใดออก

StepPageFIFO หลังเรียกใช้ผลLRU หลังเรียกใช้ผล
11[1, -]Fault[1, -]Fault
22[1, 2]Fault[1, 2]Fault
31[1, 2]Hit[1, 2]Hit
43[3, 2]Fault[1, 3]Fault
51[3, 1]Fault[1, 3]Hit

Step 4 เลือกเหยื่อต่างกัน แต่ทั้งคู่ยัง Fault; step 5 ผล Hit/Fault จึงต่างกัน เพราะ LRU ยังเก็บ page 1 ไว้ สรุป FIFO 4 faults / 1 hit / 2 replacements, LRU 3 faults / 2 hits / 1 replacement

สูตรที่ต้องรู้

hits + faults = references ที่ประมวลผล
fault rate = faults ÷ references ที่ประมวลผล × 100
ตัวอย่าง FIFO: 4 ÷ 5 × 100 = 80% ถ้าหยุดก่อนจบ ใช้จำนวนขั้นที่ประมวลผล/แสดงจริงเป็นตัวหาร

ความหมายของการค้นหา

ให้ K เป็นจำนวน page IDs และ N เป็นความยาว reference string จะมี KN ชุด โปรแกรมไล่ candidate เหมือนเลขฐาน K และเรียก engine กับแต่ละชุด หยุดเมื่อพบตัวอย่างแรก ตรวจครบ หรือถึง limit

สถานะสรุปได้แค่ไหน
SEARCH_FOUNDมี input ที่ตรงเงื่อนไขในขอบเขตนี้ ไม่ได้อ้างว่าสั้นที่สุด
SEARCH_EXHAUSTEDไม่พบหลังตรวจครบ space ที่ตั้งไว้ ไม่ได้พิสูจน์ว่าไม่มีในขอบเขตอื่น
SEARCH_LIMIT_REACHEDตรวจเพียงส่วนต้น ยังมี candidate ที่ไม่ถูกตรวจ
SEARCH_INVALIDConfiguration ไม่ถูกต้อง ไม่ใช่ผลทดลองว่าไม่พบคำตอบ

โครงสร้างข้อมูลกลางที่ต้องรู้ร่วมกัน

  • ReferenceString: array หมายเลข page กับ count
  • Step: snapshot หลังเรียกหนึ่ง page เก็บ frames, fault, evicted page, slot และ reason
  • Stats: hits, faults, replacements
  • SearchConfig / SearchResult: ขอบเขต เงื่อนไข จำนวนชุดที่ลอง และคำตอบที่พบ
  • ResultCatalog: รายชื่อไฟล์ที่อ่านได้ใน results พร้อมจำนวน references

Callback คือฟังก์ชันที่ engine เรียกหลังจบหนึ่ง step เพื่อให้ผู้รับแสดงผลหรือคัดลอก snapshot ได้ Search ใช้ callback เป็น NULL เพื่อคำนวณ Stats อย่างเดียว

สิ่งที่ทุกคนควรพูดให้ตรงกัน

  • Page 0 ถูกต้อง; ช่องว่างใช้ EMPTY_PAGE = -1
  • ทุก run เริ่มด้วย frame ว่าง ต้องใช้ input และ frames เดียวกันเพื่อเทียบ algorithm
  • LRU ไม่ชนะ FIFO ทุก input และการเพิ่ม frame ไม่ได้ลด faults เสมอใน FIFO
  • ไฟล์ที่ save เก็บแค่ reference string ต้องจำ/บันทึก frames แยกเอง
  • บน Windows results อยู่ข้าง build ของโปรเจกต์; full path ยังเปิดไฟล์นอก results ได้
PERSON 01

เจ้าของ Algorithms และการค้นหา

ต้องอธิบายได้ว่า engine ตัดสินใจอะไร เก็บสถานะอย่างไร และ search นำ engine ไปทดลองซ้ำอย่างไร

ลำดับอ่านโค้ด

  1. src/simulator.h
    อ่าน enum Algorithm, EMPTY_PAGE และ struct ทั้งสาม มองว่า Step คือข้อมูลส่งออกของหนึ่งขั้น ส่วน Stats คือผลสะสมของหนึ่ง run
  2. src/simulator.c → simulate()
    ไล่ validation → ตั้ง frames ว่าง → วน references → ค้นหา hit → หา frame ว่าง → เลือก victim → อัปเดต → callback
  3. src/search.h
    อ่าน SearchCondition, SearchConfig, SearchStatus และ SearchResult แยก total space ออกจาก tested และ limit
  4. src/search.c
    อ่าน search_candidate_count() → next_candidate() → search_references() แล้ว trace input ชุดเล็กด้วยมือ
  5. tests/test_simulator.c + tests/test_search.c
    ให้คนที่ 3 ช่วยดูว่า test ตรวจสิ่งที่อธิบายไว้จริงหรือไม่ ไม่ใช้แค่ “โปรแกรมไม่ crash” เป็นหลักฐาน
ตัวแปร/ฟังก์ชันต้องเข้าใจอะไร
frames[]สถานะ resident pages ของ run นี้ เปลี่ยนเมื่อโหลดหรือแทนที่
fifo_nextชี้ตำแหน่ง FIFO ถัดไป เลื่อนเมื่อโหลด ไม่เลื่อนเมื่อ hit
last_used[]เก็บ index การใช้ล่าสุดของแต่ละ frame อัปเดตทุก access และใช้ค่าน้อยที่สุดเลือกเหยื่อ LRU
farthest / nextOptimal ค้นหาการใช้ครั้งถัดไป ถ้าไม่พบใช้ count เป็น sentinel กรณี tie เก็บ frame ต่ำสุด
step.evicted_pageเป็น EMPTY_PAGE เมื่อ hit หรือโหลดช่องว่าง ช่วยแยก fault กับ replacement
next_candidate()เพิ่มหลักขวาสุด หากเต็มให้กลับเป็น 0 แล้วทดไปหลักซ้าย ไม่ต้อง recursion
budgetค่าเล็กกว่าระหว่าง total และ limit เพื่อไม่ค้นหาเกิน space/ขีดจำกัด
เปิดดูโค้ดสำคัญ: ข้อมูลออกจาก engine ผ่าน callback
last_used[slot] = i;
step.slot = slot;
memcpy(step.frames, frames, sizeof(frames));
if (callback && !callback(&step, context)) break;

คัดลอก frame ลง Step ก่อนส่งให้ผู้รับ ถ้า callback คืน 0 ให้หยุด run ส่วน simulate() ยังคืน 1 เมื่อ configuration ถูกต้อง แม้ถูกหยุดก่อนครบ references

เปิดดูการนับ candidate แบบเลขฐาน K
size_t position = references->count;
while (position > 0) {
    --position;
    if (++references->pages[position] < page_count) return;
    references->pages[position] = 0;
}

K=3: 0 0 2 → 0 1 0 ไม่ข้ามชุดและไม่ใช้ random Seed จึงไม่จำเป็นสำหรับ search ปัจจุบัน

ความรู้ C ที่ต้องลงลึก

  • Array กับ index: ภายในเริ่มที่ 0 แต่ข้อความแสดง step เริ่มที่ 1
  • Struct assignment: result->references = candidate คัดลอก array ที่อยู่ใน struct ด้วย
  • Pointer parameters: engine เขียน Stats ให้ caller และ callback รับ context ของผู้เรียก
  • enum, size_t, unsigned long, modulo และขอบเขตค่าที่คูณได้
  • ความซับซ้อน: FIFO/LRU ของโค้ดนี้ O(NF), Optimal O(N²F); search สองนโยบาย O(CNF) ส่วนจำนวน candidates ทั้งหมด KN
โจทย์ที่ต้องทำได้ด้วยมือ

1) คำนวณ FIFO/LRU บน 1 2 1 3 1, F=2
2) อธิบาย 0 0 1 0 2 3 1, F=3 ว่าทำไม FIFO ได้ 4 faults แต่ LRU ได้ 5
3) ไล่ candidate ของ K=2, N=3 ทั้ง 8 ชุด แล้วแยก exhausted กับ limit

สิ่งที่ต้องส่งต่อให้ทีม

อธิบาย interface simulate() และ SearchResult ให้คนที่ 2 ใช้ได้ และให้คนที่ 3 ตรวจว่าผลที่พบตรงเงื่อนไขด้วย engine อีกครั้ง อย่าเขียน engine ซ้ำในเมนูหรือส่วนทดสอบผลค้นหา

PERSON 02

เจ้าของเมนู Workflow และการแสดงผล

ต้องพาผู้ใช้จาก “เลือกข้อมูล” ไปถึง “อ่านเหตุผล” ได้ และแสดงผลที่ตรงกับสิ่งที่ engine คำนวณ

ลำดับอ่านโค้ด

  1. src/main.c → main()
    ดู state ที่อยู่ข้ามเมนู: references, frames, algorithm และ results_directory ดูว่าเมนูใดใช้ state ใด
  2. run_search(), load_from_results(), save_to_results()
    แยก workflow ของผู้ใช้จากตรรกะ search และ file I/O เมื่อค้นพบ จึงเปลี่ยน active input/frames; ถ้าไม่พบเก็บของเดิม
  3. src/display.c → run_display(), show_step()
    ดู format frames, callback, คำสั่ง Enter/a/q และการนับสถิติส่วนที่รันไปแล้ว
  4. compare_traces(), capture_step(), count_step()
    คัดลอก snapshot ของทั้ง FIFO/LRU ก่อนแสดง และนับเฉพาะ steps ที่แสดงเมื่อผู้ใช้หยุด
  5. compare_algorithms(), frame_sweep()
    ดูวิธี reset ทุก run และคำนวณผลเปรียบเทียบโดยไม่ต้องพิมพ์ trace ทั้งหมด

เมนูเชื่อมกับฟังก์ชันไหน

เมนูฟังก์ชันหลักเจ้าของที่ต้องประสาน
1 โหลด / 11 บันทึกload_from_results() / save_to_results()คนที่ 3: results และ parser
2 frames / 3 algorithmvalidation และอัปเดต state ใน main()คนที่ 1: ขอบเขต engine
4 ทีละขั้น / 5 ทั้งหมดrun_display()คนที่ 1: StepCallback
6 เปรียบเทียบ / 8 sweepcompare_algorithms() / frame_sweep()ทั้งทีม: การทดลองที่ยุติธรรม
7 ดู inputshow_references()ทั้งทีม: ตรวจข้อมูลก่อนสาธิต
9 ค้นหาrun_search() → search_references()คนที่ 1: สถานะและผลค้นหา
10 วิเคราะห์ FIFO/LRUcompare_traces()ทั้งทีม: เหตุผลของความต่าง

จุดที่ต้องอ่านให้ละเอียด

  • ask_integer() รับ Enter เป็นค่าเริ่มต้น และตรวจช่วงค่าก่อนใช้
  • เมื่อ search พบคำตอบ จะเปลี่ยน references กับ frames แต่ไม่เปลี่ยน algorithm ที่เลือกไว้
  • format_frames() รวม frame เป็น [1, -] และคำนวณความกว้างคอลัมน์จากจำนวน frame/หลักของ page
  • โหมดเดี่ยวใช้ callback ระหว่าง engine ทำงาน; โหมดสองฝั่งคำนวณ trace ครบก่อนแล้วค่อยเล่นทีละแถว
  • เมื่อหยุดโหมดสองฝั่งต้องนับผลเฉพาะที่แสดง ไม่ใช้ full Stats ไปสรุปว่าผู้ใช้เห็นครบแล้ว
  • จุด “replacement decision ต่างกัน” ตรวจ evicted page; จุด “Hit/Fault ต่างกัน” ตรวจ fault flag จึงเป็นคนละเหตุการณ์
เปิดดูโค้ดสำคัญ: คัดลอก Step แทนการเก็บ pointer ชั่วคราว
static int capture_step(const Step *step, void *context)
{
    TraceContext *trace = context;
    trace->steps[step->index] = *step;
    return 1;
}

Step ของ engine อยู่ใน stack และใช้ได้ใน callback ขณะนั้น การ copy ลง array บน heap ทำให้แสดงย้อนหลังได้ ต้องตรวจ malloc และ free เมื่อเสร็จหรือเกิด error

ความรู้ C ที่ต้องลงลึก

  • Function pointer กับ void *context: ส่งข้อมูลของส่วน display ผ่าน interface กลาง
  • malloc/free: ใครจอง ใครเป็นเจ้าของ และต้องคืนหน่วยความจำในทาง error ด้วย
  • printf field width / snprintf: ระยะคอลัมน์และขนาด buffer
  • UI state กับ simulation state: state เมนูอยู่ข้ามรอบ แต่ frames ภายใน engine เริ่มใหม่ทุก run
  • การนับผลบางส่วน: count_step() และจำนวน shown สัมพันธ์กับ Stats อย่างไร
โจทย์ซ้อม

โหลด lru_wins → ตั้ง 2 frames → เมนู 10 โหมด 1 → หยุดหลังแถวแรก ต้องรายงานหนึ่ง step และไม่มีเหตุการณ์ step 4/5 ในการวิเคราะห์ จากนั้นรันใหม่ให้ครบและอธิบายความต่าง

04

คำถามสำหรับซ้อมตอบอาจารย์

ผลัดกันถามโดยไม่อ่านหน้าจอ ให้ผู้ตอบอธิบายประมาณ 30–60 วินาที แล้วให้เพื่อนอีกคนตรวจจากโค้ดหรือเปิดเฉลย

ทุกคนต้องตอบได้

1. โปรเจกต์นี้ทำอะไร และมีอะไรนอกขอบเขต?
จำลอง page replacement ของ reference string หนึ่งชุด เริ่มด้วย frame ว่าง เปรียบเทียบ FIFO/LRU/Optimal และค้นหา input ตามเงื่อนไข ผลหลักคือ faults กับ trace ไม่ได้จำลอง TLB, address translation, disk timing, dirty bits หรือหลาย process จึงไม่ใช้ผลนี้อ้างประสิทธิภาพระบบจริงทั้งหมด
2. ทำไมทั้ง “LRU ชนะ” และ “FIFO ชนะ” จึงเกิดขึ้นได้?
ทั้งคู่ใช้ข้อมูลในอดีตคนละแบบ ลำดับ access บางชุดทำให้ page ที่ FIFO เก็บไว้ได้ใช้ต่อ ในขณะที่ LRU เอาออก ตัวอย่าง F=3, 0 0 1 0 2 3 1 ได้ FIFO 4 / LRU 5 faults หลักฐานนี้หักล้างคำว่า LRU ชนะทุกชุด แต่ไม่ได้พิสูจน์ว่า FIFO ชนะโดยเฉลี่ยทุก workload
3. ทำไมเพิ่ม frame แล้ว FIFO faults อาจเพิ่ม?
การเปลี่ยนความจุเปลี่ยนลำดับการโหลดและเหยื่อใน FIFO จึงอาจทำให้ state ในอนาคตแย่ลง ตัวอย่าง 1 2 3 4 1 2 5 1 2 3 4 5 ได้ 9 faults ที่ 3 frames และ 10 ที่ 4 frames เรียก Belady's anomaly ควรเปิดเมนู 8 แสดงหลักฐานและไม่สรุปว่าทุกครั้งที่เพิ่ม frame จะเกิด anomaly

คนที่ 1: เหตุผลของการคำนวณ

4. ไล่ flow ของ simulate() ตั้งแต่รับ input จนส่งผลหนึ่ง step
ตรวจขอบเขตและเลข page → clear Stats/frames → หา page ปัจจุบันใน frames → hit หรือ fault → หาก fault หา empty slot ก่อน → ถ้าเต็มเลือกเหยื่อด้วย policy → อัปเดต frames และ last_used → คัดลอกลง Step → เรียก callback ถ้ามี ผู้รับสั่งหยุดได้ แล้ว engine คืนสถานะ configuration
5. ทำไม search สร้าง candidate ด้วยเลขฐาน K และ K^N มีผลอย่างไร?
แต่ละตำแหน่งเลือก page ได้ K ค่า ลำดับยาว N จึงมี K^N ชุด การเพิ่มค่าจากขวาพร้อม carry ครอบคลุมทุกชุดตามลำดับ เมื่อ K/N เพิ่ม space โตแบบยกกำลัง จึงมี search limit และต้องแยกไม่พบหลังตรวจครบจากถึง limit ก่อนครบ
6. ตัวอย่างที่ search พบเป็น input สั้นที่สุดหรือไม่?
ไม่อ้างว่าสั้นที่สุด เพราะตรวจเฉพาะความยาวที่ตั้งและหยุดที่ตัวอย่างแรกในลำดับนั้น หากจะพิสูจน์ shortest ภายใต้ alphabet เดิม ต้องตรวจทุกความยาวที่สั้นกว่าครบก่อน หากถึง limit ก็ยังพิสูจน์แม้แต่ space ปัจจุบันไม่ได้

คนที่ 2: ความถูกต้องของสิ่งที่แสดง

7. ทำไมต้องแยกจุดที่เลือกเหยื่อต่างกันจากจุดที่ Hit/Fault ต่างกัน?
เหยื่อที่ต่างกันเปลี่ยนสิ่งที่เหลืออยู่ แต่ในขั้นที่แทนที่ทั้งคู่ยังอาจ fault เหมือนกัน ผลต่างอาจเห็นในการเรียกใช้ครั้งถัดไป ตัวอย่าง 1 2 1 3 1, F=2 แยก decision ที่ step 4 กับ outcome ที่ step 5 โปรแกรมตรวจ evicted_page กับ fault flag คนละเงื่อนไข
8. ทำไม capture_step() ต้องคัดลอก struct และใช้ malloc?
Step ของ engine เป็นตัวแปรชั่วคราวใน stack เก็บ pointer ไว้ใช้ภายหลังไม่ได้ จึง copy snapshot ลง array ที่จองขนาดตามจำนวน references เพื่อแสดง trace ของสอง algorithms ต้องตรวจการจองล้มเหลวและ free ทุกทางออก
9. ผู้ใช้กด q แล้ว Stats ของโหมดสองฝั่งควรเป็นอย่างไร?
แม้ engine คำนวณ trace ครบก่อนแสดง แต่ UI ต้องรายงานเฉพาะแถวที่ผู้ใช้เห็น ใช้ count_step สะสมถึง shown และวิเคราะห์ความต่างเฉพาะช่วงนั้น ไม่ใช้ full Stats ไปบอกว่าผู้ใช้ประมวลผลครบแล้ว

คนที่ 3: ข้อมูลและหลักฐาน

10. ถ้าโหลด input ผิดหลังมี input เดิม โปรแกรมทำอย่างไร?
Parser อ่านเข้า candidate ก่อน หาก token ผิด ตัวเลขล้น หรือไม่มีข้อมูล คืน 0 โดยยังไม่ assign result เมนูจึงแจ้ง error และเก็บ references เดิมไว้ เช่นโหลด classic สำเร็จแล้วลองไฟล์ที่มี 1 two 3
11. จะทำให้คนอื่นทดลองซ้ำได้อย่างไร?
บันทึก reference string เป็น .txt และบันทึก frames, algorithm, search condition, K, N, limit, tested ในรายงาน เพราะไฟล์ input ยังไม่เก็บ metadata โหลดด้วยเมนู 1 ตั้ง frames เดิม แล้วใช้เมนู 6/10 ตรวจผลเดียวกัน
12. tests ผ่านแปลว่าถูกต้องทุกกรณีหรือไม่?
ไม่ใช่ เป็นหลักฐานเฉพาะสิ่งที่ตรวจ แต่ชุดนี้มีทั้งผลที่ทราบคำตอบ invariants, independent oracle และ integration tests เช่น Optimal เทียบทุกทางเลือกบน 729 traces กับ search เทียบการ decode candidate อย่างอิสระ ช่วยลดโอกาสที่ implementation กับ test ผิดเหมือนกัน
